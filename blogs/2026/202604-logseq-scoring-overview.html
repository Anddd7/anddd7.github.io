Logseq 迁移打分：五个维度、三条流水线

这套迁移机制先用五个维度判断旧笔记值不值得留，再把它分进 A/B/C 三条流水线。你可以直接照着阈值、CSV 字段和校准步骤执行。

2026-04-13约 8 分钟阅读
#domain #logseq #migration #knowledge-management

整理 Logseq 旧笔记时，最难的不是搬运，而是判断什么该留。我的做法是先用五个维度打分，再按阈值分进三条流水线：立即吸收、延后总结、谨慎放弃。这样迁移不是凭感觉删留，而是一套能复查、能校准的流程。

执行层可以先记住一句话：高价值、强相关、可复用的进 Lane A；暂时有价值但不值得立即精炼的进 Lane B；低分、重复、偏题的进 Lane C。 难点不在公式，在于五个维度到底各自筛什么。

五个打分维度，分别在筛什么 ​

这套 rubric 对应五个字段：goal_alignment、reusability、uniqueness、insight_density、maintainability。它们不是一组漂亮指标，而是五个不同判断问题。

维度主要在看什么高分信号低分信号
goal_alignment是否服务当前知识库目标核心主题、可直接服务输出偏题、与主线无关
reusability能否跨场景复用方法、规则、框架一次性记录、强依赖上下文
uniqueness是否重复劳动独有表达、案例、结构重复摘录、简写变体
insight_density单位篇幅里是否有判断结论、边界、建议只有材料，没有提炼
maintainability迁入后是否好维护边界清楚、便于引用主题散、维护成本高

flowchart TD
  score[五维打分] --> check{是否重复 / 偏题?}
  check -- 是 --> laneC[Lane C\nDrop]
  check -- 否 --> total{total_score >= 18?}
  total -- 否 --> mid{11-17?}
  total -- 是 --> goal{goal_alignment >= 4?}
  goal -- 是 --> laneA[Lane A\nIngest-Now]
  goal -- 否 --> laneB[Lane B\nSummarize-Later]
  mid -- 是 --> laneB
  mid -- 否 --> laneC

1. goal_alignment：这条笔记是否服务当前知识库目标 ​

这一维看的是“它和当前迁移目标有没有关系”。迁移优先的是可复用的方法、框架和长期知识，所以核心主题天然比泛知识更容易得高分。最直接的判断方法，就是问一句：迁入后，能不能稳定服务当前知识库目标或后续输出？

判断很简单：强相关就高，弱相关就低，无关就直接降级。

比如 DDD.md、4+1 View Model.md、分析工具___MECE.md、架构治理.md 本身就在高价值主题里，天然更贴近目标。相反，多巴胺.md、虚数与复数.md、老头晒太阳.md 这类内容，至少在当前目标下不占优先级。

2. reusability：这条笔记能不能跨场景复用 ​

可复用性看的是“它能不能反复拿出来用”，而不是“我当时写得顺不顺”。高分内容通常能脱离原始语境单独成立，描述的是方法、框架或判断规则，而不是一次性记录。像 DDD 拆解、架构风格对比、认知偏差总结，通常都更适合进入可复用知识层；零散问答、瞬时灵感、会议碎片则更适合先放进 Lane B。

迁移计划把 Lane B 设计成 summary bundles，承认的是一个简单事实：有些材料是“主题有价值，单条不值得精修”。 它们不该丢，但也不该占用 Lane A 的处理能力。

3. uniqueness：这条笔记是不是重复劳动 ​

独特性解决的是迁移里最常见的问题：看起来在积累，实际是在重复记录。所以计划里才会先建 duplicate-clusters.md，再判断一条笔记到底是 canonical source，还是重复变体。

重复簇典型问题处理方式
DDD family同一主题多次展开找 canonical source
architecture style comparisons对比维度重复合并成主题包
cognition micro-bias notes碎片化但高度相似汇总后再提炼
overlapping workshop Q&A notes问答内容互相重叠保留最完整版本
  • 如果一条笔记提供了别处没有的表达、案例或结构，它的独特性更高。
  • 如果它只是另一条笔记的简写版、重复摘录版、局部展开版，它的独特性就应下降。

这一步看不清，迁移后的知识库就会继续继承旧系统里的冗余。

4. insight_density：单位篇幅里有没有真正的判断 ​

信息密度看的是“有效判断”有多少。高密度笔记通常有结论、有边界、有可执行建议；低密度内容则往往只有标题、概念或摘录，没有真正的提炼。这样的材料不是没用，但更像原材料，更适合先留在 Lane B 的主题汇总里。

迁移计划采用“先 synthesis，再 evidence，再 pages”的链路，本质上也是在提高 insight density：先合并原始材料，再提炼能站住脚的判断，最后才进入长期知识层。

5. maintainability：迁进去之后，未来好不好维护 ​

这一维决定知识库会不会越迁越重。好维护的内容，边界清楚、结构稳定、后续容易合并和引用；难维护的内容，通常语义发散、主题过宽、又强依赖当时上下文。计划要求 inventory.csv 记录 primary_category、secondary_category、decision_reason，就是为了提前把维护成本显式化。

阈值规则：吞吐控制 ​

计划文档给出的阈值很明确：

  • total_score >= 18 且 goal_alignment >= 4 → Lane A
  • 11-17 → Lane B
  • <=10 或 duplicate / off-goal → Lane C

我最在意的是 Lane A 额外要求 goal_alignment >= 4。这说明体系的优先级是先看是否服务当前目标，再看综合价值。

Lane A：立即吸收，不等以后 ​

Lane A 对应 Ingest-Now。进入这一道，说明材料不仅整体价值高，而且和当前知识库目标强相关，值得立即投入精炼成本。

典型候选就是首波种子里的 DDD、架构、方法论、认知类核心笔记。它们会先进入 raws/*-core-synthesis.md、raws/*-core-evidence.md，再提升到 pages/DDD.md、pages/架构模式.md、pages/问题分析与决策方法.md 等正式页面。Lane A 的意思很简单：进入生产线。

Lane B：主题保留，但先做批处理 ​

Lane B 对应 Summarize-Later。总分落在 11-17，意味着它不是垃圾，也不是当前最该精修的对象。

这类内容的正确处理方式，是进入主题包。例如计划里的：

  • raws/DDD-extended-notes-summary.md
  • raws/architecture-styles-comparison-summary.md
  • raws/cognitive-bias-and-heuristics-summary.md

这背后的判断很实用：有价值，但价值主要体现在“成组后更有用”。 如果强行逐条精炼，成本会高于收益。

Lane C：先记账，后复核 ​

Lane C 对应 Drop，但计划对它很克制。规则写的是 <=10 或 duplicate / off-goal 可进 Lane C，同时又明确规定：任何物理删除都要等完整流程结束后的最终复核和显式确认。

这点我很认同。Lane C 的意义是先停止继续投资。

也就是说，Lane C 更像一个带账本的冻结区：

  • 先记录它为什么被放弃。
  • 先标记它是不是重复、偏题或低价值。
  • 直到全量分类完成，再统一回看是否真的删除。

这样能防止迁移前期因为判断标准还没稳定，就误删边界内容。

真正让这套机制可执行的是把打分记录为 CSV，而非仅依赖口头约定 ​

如果只说“我们用五维评分”，这套机制很快就会退化成主观印象。真正让它可执行的是 inventory.csv。

初始化命令里已经把字段定义清楚了：

  • filename
  • primary_category
  • secondary_category
  • goal_alignment
  • reusability
  • uniqueness
  • insight_density
  • maintainability
  • total_score
  • lane
  • duplicate_cluster
  • decision_reason
  • status

这些字段一起工作，才把“打分”变成“治理”：

  • status 追踪是 unclassified 还是 classified。

这比在笔记边上随手写一句“感觉挺重要”强得多，因为你可以直接核对、统计、抽查，也能把争议样本翻出来重判。

实操时，最容易踩坑的是校准 ​

计划里的执行顺序很稳：先建控制面，再建全量 inventory，再建 taxonomy 和 duplicate cluster，再做 lane queue，最后只挑 20 条做第一批分类。

这个顺序说明了一个重要原则：不要一上来就全量开打。

更稳的做法是先用 inventory.csv 保证全量可见，再挑 20 条高优先级笔记做首批标注，记录争议样本后校准口径，等口径稳定了再扩大批量。

计划里的首批 20 条优先选 DDD、methodology、cognition，就是因为这些主题既重要，又相对容易形成稳定规则，适合先做标注校准集。

如果这一步跳过，后面最常见的问题就是：同样价值的两条笔记，因为不同时间、不同人、不同心情，最后被送进不同 lane。到这一步，评分就会变成幻觉，知识治理也无从谈起。

三个执行细节，决定迁移会不会失控 ​

1. raws/logseq 必须保持只读 ​

迁移计划明确要求旧笔记源保持只读。这样才能保留证据源，避免一边参考一边改原件，最后无法确认原始内容。

2. pages 不能直接引用 raws/logseq ​

决策日志里明确写了：pages 应引用 refined raws evidence files，而不是直接引用 raws/logseq。这等于在旧笔记和正式知识之间增加了一层编译层。

好处很直接：正式知识页依赖的是已经过筛、去重、提炼后的证据，而不是历史碎片本身。这样后续知识页会稳定很多。

3. 每次批处理都要留核验命令 ​

计划里不只写了流程，还写了核验方式：

核验重点很直接：源文件数要能对上 inventory 行数，unclassified 要可统计，已分类批次要能被命令复核。它的价值不在技术炫耀，而在于你能快速发现漏记、漏标或进度虚报。

这套机制最终筛选出的，是注意力分配，而非单纯分数 ​

Logseq 迁移最容易犯的错，是把“保留信息”当成目标。这个框架反过来做：先定义什么值得留下，再决定怎么处理它。

五维打分解决价值判断，A/B/C 三条流水线解决处理优先级，CSV 和核验命令解决执行可追溯性。三者缺一个，这套机制都会退化：只有分数，没有 lane，会卡在决策；只有 lane，没有字段，会无法复查；只有流程，没有目标，就会把旧噪音完整迁入新系统。

如果你也要做类似迁移，务实的起点是先挑 20 条高价值样本，把分歧记下来，再用这些分歧反推阈值和评分口径。规则不是先验真理，它应该先服务迁移过程，再随着样本逐步稳定。
